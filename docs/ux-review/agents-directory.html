The agents directory — one affordance, two destinations

Four findings on /agents/, worked as one change because they share a fix. Measured against the built site at commit d71a719. Every card below is a real entry from src/data/site.ts.

0 — What the audit found

#FindingMeasured
1 30 cards, one visual language, three kinds of destination — 4 in-site pages, 25 GitHub repos, 1 other hosted site. No signal which. 4 / 25 / 1 High

24px tall		 High
3 Intro says “Every entry links to its public repository.” Five no longer do. 5 / 30 false Medium
4 Six groups, no jump list, no anchors, no counts. Groups are only findable by scrolling past them. 30 entries Medium

Findings 1 and 2 have the same fix, and it is a small one: the data layer already knows which entries are in-site, because their url starts with /. Nothing new needs to be stored and no content needs rewriting — the distinction just needs to be rendered.

    2 — Telling the two destinations apart

    Three ways to signal it, in increasing strength. All three are shown against real entries: colleague and lobes-cli have pages, the rest do not.

    OptionReads at a glanceCostRisk
    A — label + glyph
    “Read the page →” vs a repo glyph    		 Strongest One derived boolean, one line of markup Adds a line of height per card
    B — glyph only
    A small mark in the corner    		 Moderate Lowest — no layout change Glyphs alone are learned, not read; needs assistive text
    C — separate the groups
    Pages promoted above the fleet    		 Strongest Highest — reorders the page Breaks the existing “grouped by what it does” model

    Recommendation: A. It is the only one that states the difference in words rather than asking the visitor to infer it, and it costs one derived boolean:

    const hasPage = agent.url.startsWith("/");

    C is worth revisiting when there are more than about ten presentation pages. Today, with four, promoting them above the six existing groups would fight the page's own organising idea for a section that would hold four cards.

    3 — Wayfinding at thirty entries

    A jump list with counts, and id anchors on each group so a group is linkable. The filter is a progressive enhancement — with JavaScript off, the jump list is plain anchor links and everything still works.

    Proposed — jump list, anchors, optional filter
    • Group headings get ids, so /agents/#edge-robotics becomes a shareable link — useful when pointing an agent or a person at one part of the fleet.
    • Counts set expectations before the scroll starts.
    • The filter announces its result count via role="status", so a screen reader hears the list change.
    • Filtering hides groups that empty out, so there are no orphan headings.

    4 — The intro sentence

    Finding 3 is one string in src/data/site.ts. Current:

    This is a curated selection of the fleet, grouped by what each agent does. Every entry links to its public repository.

    Suggested, once the cards distinguish themselves:

    This is a curated selection of the fleet, grouped by what each agent does. Some have a page here; the rest link straight to their public repository.

    The replacement is a stronger sentence than a merely accurate one: it tells the visitor the presentation pages exist, which the current copy actively conceals.

    5 — What this does not change

    • No new colour, font, radius or shadow. Every value is an existing token.
    • No change to the six groups or their order.
    • No change to any role text or repo name.
    • No JavaScript required for anything except the filter, which is additive.
    • Heading order stays h1 → h2 → h3, unchanged.
