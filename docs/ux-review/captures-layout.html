Captures section — three ways to kill the whitespace

Historical exploration. Option D was the strongest gallery treatment measured here, but it is no longer the intended end state. The later guided-session handoff and preserved full-page mock supersede this layout recommendation.

Measured on the live page at 1280×720. All three options below use the real captured transcripts, so the card heights are truthful. Colour and content unchanged.

What is actually causing it

The ten captures are not one gallery. They are five separate .term-grid containers, each holding exactly two figures. Each pair is sized independently, so a short card can never borrow the space left by its tall neighbour — the gap below it is structural, not a styling oversight.

The legibility problem underneath

The transcripts do not render at 12.48px. pre is 12.48px, but code and .tl inside it shrink again by .82em, so the actual rendered transcript text is 10.23px — and the elision notes, shrunk once more, land at 8.70px. Nobody chose those numbers; they are what em compounding produces through three nested levels.

This is the same root cause as the fractional spacing, but here it costs legibility rather than rhythm. Both mocks below set the size once on pre and let it inherit. The cards get taller as a result — that is the honest price of readable text, and it is an argument for Option B rather than against the fix.

Option A — masonry, the gallery pattern

CSS multi-column. Uniform gap, cards at their natural height, no dead space. This is what you described, and it does exactly what it promises.

  • Reading order changes. Columns flow top-to-bottom then across, so you read captures 1–5 down the left, then 6–10 down the right. These captures are a pipeline narrative — scope, frame, challenge, plan, deviate, summary — so that reordering has a cost.
  • The section gets very long. Removing the dead space does not remove the content; the tallest transcript is ~19,500 characters. Scroll the mock and you will feel it.
  • grid-template-rows: masonry is not broadly shipped, so multi-column or JS are the real choices today. Multi-column needs no JS, which is why it is used here.
Option A — masonryno dead space · reading order changes

Option B — uniform grid, capped, scrolls inside

Every card the same height; the transcript scrolls within it. No dead space either, but the section stays a fixed, scannable size and the sequence survives.

  • Reading order is preserved — left to right, in the order the pipeline runs.
  • The tallest card today is 1084px, which nobody reads as a static block anyway. Terminals scroll; this is the honest metaphor rather than a decorative one.
  • The section becomes scannable. Ten equal cards read as a set you can survey, rather than a wall you must scroll past to reach the next section.
  • The cost: content is hidden behind a scroll, so the page no longer shows everything at once. A bottom fade signals there is more.
Option B — capped & scrollingno dead space · order preserved

Option C — one column, full width

The whitespace problem exists because there are two columns. Remove the second one and no mismatch is possible — there is no neighbour to be shorter than. Cards take their natural height, nothing is capped, nothing is hidden, nothing reorders.

  • Wide lines are the native format for terminal output. At full width the transcripts wrap roughly half as much, which is why this is not simply “twice as tall as two columns”. Less wrapping is also genuinely easier to read — wrapped monospace is the thing that makes transcripts hard to follow.
  • Nothing is hidden and nothing is nested. No scroll-within-a-scroll, which is the real cost of Option B — nested scrolling is awkward on a trackpad and worse on touch.
  • Order is exact, and the section reads as a chronology rather than a grid.
  • The cost is honesty about length. At 6300px this is the longest of the three — but only 1.3× Option A, not 2×, because of the reduced wrapping. It does not pretend the content is smaller than it is.
Option C — single columnnothing hidden · nothing reordered

Option D — capped preview, expands in place

The compact-but-complete answer. Cards are capped to a preview height and clipped — not scrolled — and any card whose content is cut gets an expand control. Opening a card spans it across both columns at full width, where it wraps less and reads better than it could in either grid.

  • It removes Option B's worst trait. Nothing scrolls inside anything. Nested scrolling is the thing that makes B awkward on a trackpad and genuinely bad on touch; here the page scrolls and cards open.
  • max-height, not height. A genuinely short card — deviate is 226px — stays short instead of padding itself out to a uniform size with empty dark space. Dead space inside a card reads as a bug; a short card next to a tall one reads as content.
  • Expanded is the best reading mode on the page. Full width means far less wrapping, so an opened card is shorter and clearer than the same transcript in Option C's single column.
  • Order survives. Cards open in place, so the sequence never changes.
  • The cost: it needs JavaScript. About fifteen lines. A CSS-only version is possible with <details>, but that cannot show a clipped preview — closed means empty — and the checkbox-and-label alternative has real accessibility problems. A button with aria-expanded is the honest way to build this.
  • The fade is applied only where content is actually clipped, measured after layout — so short cards do not get a fade over empty space, and their expand control is removed rather than left to do nothing.
Option D — expand in placecompact · complete · nothing nested

Recommendation

The measurement undercuts Option A. Masonry sits in the middle on height (4840px) while being the only one of the four that reorders the captures. It pays a real cost — a pipeline narrative read out of sequence — and does not buy the shortest section in return. On these numbers it is hard to argue for.

Option D is the strongest of the four. It matches Option B's 2496px collapsed — the shortest of the four — while removing every one of B's costs. Nothing scrolls inside anything. Nothing is permanently hidden. Order is preserved, verified with a card open. And an expanded card is the best reading mode on the page: at full width the transcript wraps so much less that capture 1 shows completely in 607px, having needed a 480px window to show a fraction of itself collapsed.

  • The real cost is the JavaScript — about fifteen lines, and a <details> version cannot show a clipped preview. If a no-JS constraint exists, that rules D out and the choice falls back to C.
  • Option C remains the best no-JS answer. 6300px, nothing hidden, nothing nested, nothing reordered. Longer, but honest and completely static.
  • Option B is now hard to justify. D matches its height and beats it on every other axis.

All four need the same markup change first: ten figures, one container.
